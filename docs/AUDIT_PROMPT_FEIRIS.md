# フェイリス式・実在仕様照合型 品質監査プロンプト

対象: GitHubリポジトリ `sylpica/Puzzle-Dragons`（公開URL https://sylpica.github.io/Puzzle-Dragons/ ）
前提: 対象は「実際にあるゲーム（パズル＆ドラゴンズ）のパズル操作を再現する、単一ファイルの練習シミュレーター」である。本監査は汎用チェックリストの適用ではなく、**実在仕様との一致・状態の不変条件・表示の整合**を中核とする。

## 第1原則（絶対）
1. 「動いた」ではなく「仕様どおりに動いた」だけを合格とする。仕様の根拠は、一次情報源または複数攻略情報源の一致で示すこと。根拠が取れない仕様は「未確認」と明記し、推測で正常扱いしない。
2. すべての指摘は、再現手順と実測値で示す。再現できない指摘は「疑義」として分離する。
3. テストが通ることは証拠の一部にすぎない。テスト自体が間違っている可能性を常に疑い、期待値はアプリの出力ではなく仕様から導く。
4. 修正は根本原因に対して行い、仕様を変えて辻褄を合わせない。表示文言と挙動が食い違う場合は、どちらが仕様かを根拠で決めてから直す。

## 監査1: 実ゲーム仕様との照合（ゲーム忠実度）
以下を一次情報源・複数情報源で照合し、実装値と突き合わせる。
- 盤面寸法と最大コンボ数の関係
- 毒・猛毒・爆弾・トゲのダメージ式（最大HP比）と発動順序（爆弾がコンボ解決より先か）
- 爆弾の破壊範囲（行・列）と、つながった爆弾・落とし経由の爆弾の扱い、ロック中ドロップの巻き込み
- ルーレットの色順・切替間隔の実在バリエーション・対象外ドロップ（お邪魔等）の変換規則
- 操作時間の既定値と、盤面の画面内位置（下端・全幅）の実機比
- 照合できなかった項目は未確認リストとして残す（正常と書かない）

## 監査2: 不変条件の網羅検証（状態機械）
次の不変条件を、ランダム操作ファジング（高速・斜め・往復・端マス・連打・操作中断・サイズ切替・モード切替の混在）で崩れないか検証する。
1. 解決後の盤面は常に全マス充足し、ドロップの uid は一意で、描画ノード数＝マス数
2. 補充直後の盤面に「即マッチ」が存在しない（落ちコンなしの担保）
3. 掴んだドロップは常に盤面内に1つだけ存在し、離した後に残留しない
4. タイマー表示は単調減少し、0で必ず解決が始まる（二重解決しない）
5. アンドゥは「直前の1手」だけを正確に巻き戻し、他の操作（サイズ変更・一括変更・読込）の後では作用しない
6. 編集操作はプレイ状態（ターン・ダメージ）を汚染しない

## 監査3: 表示三点整合（同一事実の複数表示）
同じ事実を表示する箇所同士が一致するか、シナリオごとに突き合わせる。
- 被ダメージ%: ステータスのピル／直近ターン結果／ダメージプ内訳 の3表示が同一ターンで一致する
- コンボ数: ポップ表示／ステータス／結果表示が一致する
- 消去数: 結果の合計と内訳（タイプ別）の合計が一致する
- ターン数: ステータスとログのターン番号が一致する
- リセット後は全表示が初期状態に揃う

## 監査4: 確率・乱数の統計検証
- 補充ドロップの色分布が一様から有意に偏っていないか（カイ二乗の目安でよい、標本数を明記）
- 目覚めON時の混入率（毒・お邪魔・トゲ）がラベル表記と矛盾しないか（実測率と標本数を報告）
- シャッフルの初期盤面にマッチが含まれないこと、偏りがないこと

## 監査5: 永続化の往復同等性（プロパティ検証）
- 保存→読込で盤面・状態・マスギミックが完全一致する（ルーレットの位相 idx を含む）
- エクスポート→インポートでも同じく完全一致する
- 往復を2回繰り返しても劣化しない
- 壊れたデータ・型違い・巨大入力・未知フィールドでは「拒否して無事」であること（部分的に読み込んで壊れた状態にしない）

## 監査6: 差分監査（前回監査からの変更点）
- 前回監査レポート（docs/QUALITY_AUDIT.md）の指摘修正が、実際に根本原因を取り除いているかコード差分で再確認する
- 修正の副作用で壊れた既存挙動がないか、過去の合格項目を全て回帰する
- 「修正した」という記述と実際の差分が一致しない項目は、未修正として扱い直す

## 監査7: テスト自体の監査（ミューテーション的検証）
- 主要な計算式（毒・猛毒・爆弾・トゲ）を意図的に壊した変異版を作り、既存テストがそれを検出できるか確認する。検出できない式は、テストの穴として報告し、テストを補強する
- テストの期待値が「現在の実装の出力」を写したものになっていないか点検する
- 測定対象の取り違え（表示値と実測値、inlineとcomputed等）がないか点検する

## 監査8: 入力現実性と性能
- 実機タッチ相当の操作（pointer events）で、取りこぼし・二重発火・捕捉漏れがないか
- ルーレット多数配置＋最大盤面（7×6）での描画負荷と、長時間プレイでの状態劣化（ノード残留・タイマー残留）がないか
- 画面回転・リサイズ・タブ切替（visibilitychange）を挟んでも操作が破綻しないか

## 進め方と完了条件
1. 監査1〜8を順に実施し、指摘は「再現済み／静的確認／疑義」に分けて記録する
2. 再現済みの欠陥は根本原因を特定して修正し、修正前後で同じテストが失敗→成功に転じることを確認する
3. 全監査項目を再実行し、新規の再現済み欠陥がゼロになるまでループする（収束）
4. 最終報告には、監査項目ごとの結果・実測値・標本数・未確認事項・修正一覧・テスト結果を含める
5. 合格の宣言は「検証範囲内で」に限定し、未検証領域（実機ブラウザ等）を明記する
